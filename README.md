# All Right — Charlie registration quiz: business-outcome coverage

Практична частина (Варіант 1) тестового завдання QA Automation Engineer. Письмовий підхід — у [`PART_A_APPROACH.md`](./PART_A_APPROACH.md).

## Що це

Один Playwright-тест, який:

1. Проходить квіз реєстрації **не знаючи наперед його кроків** (`src/quiz-navigator.ts`) — шукає відомі патерни взаємодії (data-testid → роль елемента → generic видима кнопка/поле) і рухається вперед, поки не побачить сигнал завершення.
2. Підтверджує **бізнес-результат** — акаунт створено + пробний урок заброньовано (`src/outcome-verifier.ts`) — через три незалежні сигнали (мережева відповідь / URL / generic success-елемент), а не через конкретний UI одного A/B-варіанта.

Навігація і верифікація навмисно розділені й нічого одна про одну не знають — див. `PART_A_APPROACH.md`, розділ "Як рішення переживає зміну A/B-варіанта".

## Як запустити

```bash
npm install
npx playwright install chromium
cp .env.example .env   # і за потреби скоригуй значення
npm test
```

⚠️ **Це живе середовище.** Прогін тесту створює реальний акаунт і бронює реальний пробний урок на stage. Не запускай без потреби і не запускай паралельно кілька разів поспіль без узгодження з командою (див. "Питання команді" нижче).

## Структура

```
src/quiz-navigator.ts     # проходження квіза без знання його форми наперед
src/outcome-verifier.ts   # перевірка бізнес-результату, незалежна від A/B
tests/quiz-completion.spec.ts     # e2e, живий стейдж, side-effects
tests/unit/                       # чиста логіка (hasKeyDeep, pickSyntheticValue), без браузера
playwright.config.ts      # serial/workers:1 — свідомо, через side-effects
.github/workflows/quiz-smoke.yml  # scheduled synthetic monitor, не PR-гейт
```

Юніт-тести ганяються окремо й швидко, без мережі та браузера:

```bash
npx playwright test tests/unit
```

## Припущення, які я зробив

Я **не** заходив у живий стейдж перед написанням коду — свідомо, щоб не створювати зайві тестові акаунти лише заради підбору селекторів (той самий side-effect, від якого застерігає саме завдання). Тому нижче — задокументовані припущення, а не підглянуті факти:

- Елементи квіза підтримують `data-testid` (`*-option`, `*-next`/`*-cta`/`*-submit`) АБО достатньо семантичні ролі (`role=radio/checkbox/button` з доступним ім'ям). Якщо жодного з двох немає — навігатор деградує до "перша видима кнопка/поле в `main`", що менш надійно.
- Завершення квіза супроводжується POST-запитом, чия URL містить щось на кшталт `sign-up`/`registration`/`users`/`bookings`, а тіло відповіді десь містить ідентифікатори на кшталт `userId`/`lessonId` — це параметризовано через `.env`, не зашито в код.
- Є (або може бути додано) стабільний пост-реєстраційний роут (URL patterns `welcome`/`thank-you`/`dashboard`) і/або `data-testid="signup-success"` як fallback-сигнал.
- Один прогін = один зафіксований шлях крізь один активний набір A/B-варіантів; тест не намагається навмисно перебрати всі активні експерименти за один запуск (див. "Sampling, не покриття" у Частині A).

## Питання команді

Це саме ті уточнення, які завдання прямо пропонує задати до/під час старту:

1. Чи є в квізі конвенція `data-testid` для кроків/опцій/CTA? Якщо так — де вона задокументована, щоб навігатор міг покладатись на неї як на основну стратегію, а не на fallback.
2. Який реальний ендпоінт (або GraphQL-операція) відповідає за завершення квіза, і яка структура відповіді гарантована незалежно від A/B-варіанта?
3. Чи є виділений email/phone-домен або патерн для QA-трафіку, який можна відфільтрувати з аналітики й регулярно чистити? Якщо ні — пропоную завести.
4. Чи є вебхук/подія від experiment-платформи чи репозиторію квіза, на яку можна повісити CI-тригер "запустити смоук одразу після зміни", а не тільки за розкладом?
5. Куди слати алерт при падінні (Slack-канал/PagerDuty) — з огляду на прямий вплив на конверсію платного трафіку.

## Відомі обмеження

- Навігатор не вміє взаємодіяти з по-справжньому нестандартними контролами (drag-and-drop, кастомні слайдери без ARIA-ролі) — впаде з інформативною помилкою, а не мовчки пройде повз. Список відомих cookie/consent-оверлеїв (`OVERLAY_DISMISS_SELECTORS` у `quiz-navigator.ts`) теж не вичерпний — покриває поширені паттерни (OneTrust, Cookiebot, generic dialog з "accept"/"дозволити"), не гарантовано конкретний віджет All Right.
- Верифікатор толерантний до вкладеності/перейменування обгортки відповіді, але не до перейменування самих ключів — зміна `userId` → `user_id` без попередження вимагатиме оновити `.env`.
- Один прогін не гарантує влучання в усі одночасно активні A/B-гілки.
- Код і Частина A написані й перевірені (`tsc`, `playwright test --list`, юніт-тести пройдено), але **e2e-тест жодного разу не запускався проти реального `stage.allright.com`** — свідомо, щоб не створювати зайвий акаунт/бронювання без потреби. Отже мережевий/URL-паттерн і селектори в `.env.example` лишаються задокументованими припущеннями, не перевіреним фактом.

## Що б зробив далі за наявності більше часу

- Підключив би `page.on('console')`/`pageerror` до кожного прогону і репортив JS-помилки як окремий (некритичний) сигнал, навіть якщо бізнес-результат досягнуто.
- Додав би легкий cleanup-скрипт (за API, якщо є) для видалення тестових акаунтів, створених прогонами.
- Реалізував би Варіант 2 (агентний прохід з баченням екрана через LLM) як окремий nightly canary-джоб, що доповнює цей детермінований тест саме там, де евристики навігатора застрягають.
- Додав би невеликий дашборд/лог історичних прогонів (які стратегії спрацьовували, скільки кроків займав прохід) — це саме по собі сигнал: різке збільшення кількості кроків чи зміна набору стратегій може означати новий A/B-варіант ще до того, як щось "зламалось".
